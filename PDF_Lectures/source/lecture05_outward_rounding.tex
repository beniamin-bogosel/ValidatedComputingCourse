Goal: preserve the set guarantee when inputs, operations, and outputs use finite precision.}
\heading{1. A tiny rounding error can destroy inclusion}{0--14 minutes: a failing singleton and the required one-sided contract}
Lecture 04 proved formulas over exact real or rational endpoints. A machine
implementation must preserve their inequalities. A nearest-rounded approximation
can be very accurate and still lie on the wrong side of an endpoint. For a
certificate, the direction of the error matters, not just its small magnitude.

Isolate arithmetic rounding by treating two stored binary floats as the exact
input data. Their exact rational sum need not equal the nearest-rounded float sum:
\begin{lstlisting}
from fractions import Fraction
x = Fraction.from_float(0.1)
y = Fraction.from_float(0.3)
exact_sum = x + y
rounded_sum = Fraction.from_float(0.1 + 0.3)
assert rounded_sum - exact_sum == Fraction(1, 2**55)
assert not (rounded_sum <= exact_sum <= rounded_sum)
\end{lstlisting}
The singleton with both endpoints equal to \texttt{rounded\_sum} misses the exact
answer. There is no decimal-input ambiguity in this example: the intended data
were the stored floats. If we instead intended $1/10$ and $3/10$, their conversions
would be additional operations requiring their own enclosures.

\textbf{The contract we need.} Write $\operatorname{down}(z)$ for rounding toward
$-\infty$ and $\operatorname{up}(z)$ for rounding toward $+\infty$. Their defining
properties are
\[
 \operatorname{down}(z)\le z\le\operatorname{up}(z).
\]
A representable value needs no widening. Otherwise the lower endpoint must lie
below the intended value and the upper endpoint above it. Round-to-nearest alone
provides neither one-sided promise.

\heading{2. Enclose the input before doing arithmetic}{14--29 minutes: exact parsing and MPFR conversion in two directions}
A safe input pipeline separates two jobs: identify the exact mathematical input,
then enclose it in the chosen machine format. For an intended decimal tenth, use
an exact rational $1/10$. For an intended stored float, use its exact binary
rational value. Neither input interpretation is inherently wrong, but silently
switching between them changes the problem.

MPFR supplies arbitrary-precision floating-point arithmetic with specified rounding
modes. The Python interface \texttt{gmpy2} lets us set precision and rounding in a
local context. Here we choose 24 significant binary digits, rather than relying
on whatever precision an earlier cell happened to leave active.
\begin{lstlisting}
import gmpy2

def as_fraction(value):
    numerator, denominator = value.as_integer_ratio()
    return Fraction(int(numerator), int(denominator))

intended = gmpy2.mpq(1, 10)
with gmpy2.context(precision=24, round=gmpy2.RoundDown):
    lower = gmpy2.mpfr(intended)
with gmpy2.context(precision=24, round=gmpy2.RoundUp):
    upper = gmpy2.mpfr(intended)

assert as_fraction(lower) <= Fraction(1, 10) <= as_fraction(upper)
print(as_fraction(lower), as_fraction(upper))
\end{lstlisting}
The audit recovers the exact dyadic values of the finite MPFR endpoints. It does
not compare shortened decimal display strings. Both inequalities therefore have
an exact rational interpretation.

\textbf{The order of conversion matters.} Passing \texttt{0.1} to an arbitrary-
precision constructor starts with a Python float whose conversion has already
occurred. Extra bits cannot reveal the decimal value the user may have intended.
Likewise, rounding an exact rational once to nearest and then using that same
result for both endpoints generally loses inclusion at the first step.
For a measured interval $[a,b]$, round $a$ down and $b$ up separately.

\textbf{Negative inputs expose a common mistake.} Toward zero is not the same
as downward. For a negative nonrepresentable real value, rounding toward zero
moves the result upwards. It cannot serve as a guaranteed lower endpoint.
For example, a lower enclosure of $-1/10$ must be at least as negative as $-1/10$.

\heading{3. Round the endpoint formulas, in the right direction}{29--46 minutes: prove addition and audit all multiplication candidates}
Let stored finite endpoints define $X=[a,b]$ and $Y=[c,d]$. Exact addition lies
between $a+c$ and $b+d$. Enclosing each extreme outwards therefore gives
\[
 X+Y\subseteq[\operatorname{down}(a+c),\operatorname{up}(b+d)].
\]
The same reasoning gives subtraction bounds
$[\operatorname{down}(a-d),\operatorname{up}(b-c)]$. For a denominator excluding
zero, reciprocal bounds are $[\operatorname{down}(1/d),\operatorname{up}(1/c)]$.
These formulas combine Lecture 04's set argument with the one-sided rounding contract.

For multiplication, let the four exact corner products be $p_1,\ldots,p_4$.
If $l_i\le p_i\le u_i$ for every corner, then
\[
 \min_i l_i\le\min_i p_i,\qquad \max_i p_i\le\max_i u_i.
\]
Compute all four candidates downward for the lower bound and upward for the
upper bound. A nearest-rounded list followed by a change in the rounding mode
would not undo the rounding already performed.
\begin{lstlisting}
def multiply_mpfr(X, Y, bits):
    a, b = X
    c, d = Y
    with gmpy2.context(precision=bits, round=gmpy2.RoundDown):
        lower_products = [a*c, a*d, b*c, b*d]
    with gmpy2.context(precision=bits, round=gmpy2.RoundUp):
        upper_products = [a*c, a*d, b*c, b*d]
    for product in lower_products + upper_products:
        if not gmpy2.is_finite(product):
            raise ValueError("A finite enclosure was not obtained")
    return min(lower_products), max(upper_products)

X = (gmpy2.mpfr(-2), gmpy2.mpfr(3))
Y = (gmpy2.mpfr(-4), gmpy2.mpfr(-1))
lo, hi = multiply_mpfr(X, Y, bits=24)
assert as_fraction(lo) <= -12 and as_fraction(hi) >= 8
\end{lstlisting}
The function assumes ordered MPFR endpoints representing the input sets. Integer
endpoints in the demonstration are exact. Nonfinite candidates are rejected;
handling infinite endpoints would require a broader arithmetic contract.
Results are MPFR endpoints, not Python floats converted from them afterwards.

\heading{4. Precision choices and misleading repairs}{46--61 minutes: local contexts, genuine uncertainty, and a failed shortcut}
More bits can reduce rounding width, but not every wide interval is wide because
of rounding. An enclosure of the exact number $1/3$ generally becomes narrower
when recomputed at higher precision. The measured interval $[1,2]$ must still
contain every value from one to two. No legitimate precision setting removes
that declared uncertainty.

Nor does converting previously rounded endpoints to a wider format recover the
original exact input. To refine an input enclosure, return to its exact rational,
string, or explicitly specified data set. A finer container can store an old wide
interval more accurately without making the interval itself any narrower.

\textbf{Keep arithmetic settings local.} Precision and rounding are part of the
meaning of an operation. A notebook should not depend on the order in which
unrelated cells happened to run. Context managers make the active settings visible
and restore the previous context on exit, including an exceptional exit.
\begin{lstlisting}
before = (gmpy2.get_context().precision, gmpy2.get_context().round)
with gmpy2.context(precision=80, round=gmpy2.RoundUp):
    high = gmpy2.mpfr(gmpy2.mpq(1, 3))
after = (gmpy2.get_context().precision, gmpy2.get_context().round)
assert after == before
assert as_fraction(high) >= Fraction(1, 3)
\end{lstlisting}
The course's small interval class also rejects mixed-precision interval operands.
That policy makes any change of precision explicit; it is not a universal rule
that every numerical library must adopt. Agreement between successive precisions
is useful evidence, but still does not establish a one-sided bound.

\textbf{Why not add one ulp at the end?} Widening one correctly rounded basic
operation by adjacent representable values can be justified under suitable
assumptions. It is not a general repair for a whole expression. Consider
\begin{lstlisting}
import math
rounded = (1e16 + 1.0) - 1e16
lo = math.nextafter(rounded, -math.inf)
hi = math.nextafter(rounded, math.inf)
assert not (lo <= 1.0 <= hi)
\end{lstlisting}
The exact expression on the stored input values equals one. The computed answer
is zero, whose neighbouring floats are tiny subnormals. A final one-ulp expansion
has no information about the increment lost much earlier in the evaluation.

\heading{5. Balls and endpoints: convert the sets, not their printouts}{61--77 minutes: midpoint error, radius growth, and an Arb example}
A ball $m\pm r$, with $r\ge0$, represents the real set $[m-r,m+r]$.
For exact endpoints $a\le b$, the formulas $m=(a+b)/2$ and $r=(b-a)/2$
give the same interval. On a machine, rounding $m$ can move the centre. Retaining
an unchanged radius may then exclude one of the original endpoints.

If the computed midpoint is $\widehat m=m+e$ and $|e|\le\eta$, the triangle
inequality gives, for every $x\in[a,b]$,
\[
 |x-\widehat m|\le |x-m|+|e|\le r+\eta.
\]
Thus a radius rounded upwards from $r+\eta$ is safe. Equivalently, choose a radius
at least $\max(\widehat m-a,b-\widehat m)$, evaluating these quantities with
appropriate bounds. Midpoint accuracy and radius accuracy have different roles.

Arb provides ball arithmetic through \texttt{python-flint}. One useful input
construction encloses each exact endpoint in a ball and takes an enclosing union:
\begin{lstlisting}
from flint import arb, ctx, fmpq
with ctx.workprec(80):
    left_ball = arb(fmpq(1, 10))
    right_ball = arb(fmpq(3, 10))
    ball = left_ball.union(right_ball)
    midpoint = ball.mid().fmpq()
    radius = ball.rad().fmpq()
    exact_lower = midpoint - radius
    exact_upper = midpoint + radius
    assert exact_lower <= fmpq(1, 10)
    assert exact_upper >= fmpq(3, 10)
\end{lstlisting}
Here \texttt{fmpq} is an exact rational type. A finite Arb midpoint and radius are
dyadic values, so the extracted rational endpoints describe the represented ball
exactly. These comparisons avoid an implicit conversion of the rational test
value into a wider ball. A containment predicate between two balls answers a
different question from membership of one exact rational point.

The input construction may enlarge $[1/10,3/10]$. If we subsequently evaluate a
function on that larger ball, the function must be defined there. An enclosure
bridge preserves inclusion; it does not promise identical endpoints or preserve
every domain margin automatically.
